# 提炼会话知识笔记

将当前会话中的技术探索转化为一篇自包含、可复用的学习文档。以会话为主要材料；仅在存在项目且确有必要时读取会话中已经讨论过的相关代码，不为补充篇幅而扩大检索范围。

## 工作流程

### 1. 确定提炼范围

- 回顾当前会话中的用户问题、推导过程、代码片段、反例、修正和最终结论。
- 选择用户明确指定的主题；未指定时，选择会话中最主要且最具复用价值的技术主题。
- 将能形成同一知识体系的子问题合并到一篇文档。忽略寒暄、操作过程和与主题无关的支线。
- 以讨论中经过修正后的结论为准，不并列保留已经被否定的早期判断。若结论依赖版本、配置、运行时或业务前提，明确写出适用条件。
- 当会话信息不足以支持某项结论时，缩小结论范围或标记为待验证，不凭空补全事实。

### 2. 从具体问题抽象为通用知识

- 提炼机制、因果关系、设计权衡、适用边界、常见误区和排查方法，不按聊天时间线复述问答。
- 删除公司名、业务名、真实账号、内部地址、密钥、数据库数据及其他敏感信息。
- 将项目专用的类名、方法名、表名、键名和路径改写为表达同一机制的中性名称。
- 仅当代码能显著帮助理解时加入示例。允许选取当前项目的局部代码，但应裁剪无关逻辑并泛化命名，使读者无需了解该项目也能看懂。
- 不把项目实现描述成语言、框架或中间件的普遍保证。区分规范行为、常见实现和当前代码的特定选择。

### 3. 组织文档

根据主题取舍章节，不为满足模板而填充空洞内容。优先使用以下结构：

```markdown
# <技术主题：核心问题>

> 用 2～4 句话说明核心结论、解决的认知问题以及适用范围。

## 问题与边界
## 核心概念
## 工作机制与推导
## 关键结论
## 示例
## 常见误区与易错点
## 实践建议或排查清单
## 延伸思考
```

遵守以下写作要求：

- 默认使用与用户当前会话相同的语言；中文会话默认输出中文。
- 让文档能够脱离原会话独立阅读，禁止使用“如上所述”“刚才的代码”“你的项目中”等依赖上下文的表述。
- 先解释为什么，再解释怎么做。对并发、缓存一致性、内存模型等主题，明确参与者、共享状态、事件顺序、可见性和失败场景。
- 用最小且完整的代码片段说明机制。代码块标注语言，并在代码前后说明其意图、成立条件和局限性。
- 对容易混淆的概念进行对照，但避免重复同一结论。结论应具体到读者可以据此判断或行动。
- 不生成会话逐字稿、项目修改清单、提交记录或对 AI 回答过程的评价。

### 4. 确定输出位置

- 用户已经明确提供目标文件夹时，优先使用该文件夹，不再询问保存位置。
- 先判断当前会话是否确实关联项目或工作区。不要仅因存在当前工作目录，就把用户主目录、临时目录、技能目录或其他任意目录认定为项目。
- 存在项目或工作区且用户没有另行指定路径时，将其根目录作为输出基准，并确保 `<项目根目录>/learning/` 存在。
- 不存在项目或工作区且用户尚未提供路径时，必须暂停写入并要求用户提供保存总结的目标文件夹绝对路径。不要擅自选择当前工作目录、用户主目录、桌面或临时目录。
- 用户提供路径后，确认该路径表示目标文件夹；后续直接在该文件夹中写入，不要再自动追加 `learning/`。目标文件夹不存在时可以创建；若无权访问，则说明原因并要求用户提供可写目录或完成必要授权。

### 5. 优先完善已有文档

- 确定目标文件夹后，先列出其中已有的 Markdown 文件，并根据文件名、标题、摘要和章节定位可能相关的文档。
- 完整阅读最相关的候选文档，再依据核心主题、知识边界和读者目的判断是否应当合并。不要只凭单个关键词或技术名称判定重复。
- 已有文档与本次总结属于同一核心主题时，优先更新该文档，并采用范围尽可能小的局部编辑。
- 保留原文中仍然正确的知识、有效示例、必要前提和有价值的细节；将新知识合并到最合适的现有章节，确有必要时再新增章节。
- 删除合并后明显重复、语义等价且没有新增信息的内容，但不要误删从不同角度解释机制、边界或反例的有效内容。
- 不要仅为统一措辞、调整文风或重新组织版式而重写整篇文章。只有原结构已经导致严重重复、逻辑冲突或无法容纳新知识时，才进行必要的结构调整。
- 不要降低原文的信息密度。不得用宽泛摘要替换具体机制、成立条件、推导过程、代码示例、失败场景或排查步骤，也不要为了缩短篇幅删除仍有学习价值的内容。
- 新结论与原文冲突时，先判断是否由版本、配置或适用条件不同导致；说明差异并修正文档，不要无依据地覆盖原结论。
- 仅当没有合适的已有文档，或合并后会让文档包含相互独立的主题时，才创建新文档。若多个候选都可能适合且无法可靠选择，先向用户确认要更新哪一篇。
- 新建文档时使用 `YYYY-MM-DD-<topic-slug>.md` 命名。`topic-slug` 使用简短的小写 ASCII kebab-case，例如 `2026-08-17-redis-lock-renewal.md`。
- 若新建文档的同名文件已经存在，除非用户明确要求覆盖，否则追加 `-2`、`-3` 等序号。
- 无论新建还是更新，都严格以 UTF-8 编码写入 Markdown，保留中文、代码和标点的正确字符。

### 6. 质量检查

写入后重新读取文档并逐项确认：

- 标题、摘要和正文围绕同一技术主题，且没有强绑定具体项目。
- 关键结论与当前会话最终达成的认识一致，前提和例外没有被省略。
- 示例中的命名已经泛化，不包含敏感信息，且逻辑与正文相符。
- 更新已有文档时，原有正确知识仍然保留，新知识已经合并，明显重复已经删除，且不存在无理由的整篇重写或信息密度下降。
- 文档没有依赖聊天上下文的指代，也没有虚构来源、测试结果或未讨论过的事实。
- 文件可按 UTF-8 正常读取，不含 `�`、`锟斤拷` 等乱码迹象。
- 最终向用户说明本次是新建还是更新已有文档，报告实际文件路径，并用一句话概括新增或完善的知识内容。
